# گزارش اجرای واقعی P4

## ابزار درگاه لوکال به درخواست کاربر — ۲۰۲۶-۱۰-۲۶

LOCAL_PAYMENT_SIMULATOR پیش‌فرض خاموش، فقط local و loopback واقعی؛ provider مستقل در payment_attempts/payments و گزارش با هشدار دائمی برای DB آزمایشی. schema، vendor یا dependency جدید ندارد. وضعیت سمت سرور در cache یک‌روزه؛ checkout همان نشست و تصمیم نخست زیر cache lock؛ callback عادی و settlement اصلی استفاده می‌شوند.

اجرای واقعی Windows/PHP 8.4: مجموعه کامل SQLite **۲۳۰ تست / ۱۵۶۳ assertion موفق**، شامل **۱۳ تست جدید / ۹۵ assertion**. Pint و diff --check موفق. موفق/ناموفق و retry، callback تکراری، OK جعلی بدون تصمیم، انقضا و اعتبار یک‌باره، لغو و اعتبار، مالکیت نشست، CSRF واقعی، خاموش‌شدن، production/staging، peer دور با forwarded جعلی، origin عمومی، cache گم‌شده، مبلغ نامعتبر، حفظ adapter تلاش واقعی هنگام تغییر flag و هشدار گزارش بررسی شدند. Http::preventStrayRequests و assertNothingSent مسیرهای شبیه‌سازی را بدون شبکه بانک آزمودند. تلاش اول تست به‌علت تکیه بر session ID ناپایدار شکست خورد؛ مالکیت به nonce تصادفی خصوصی داخل نشست تغییر کرد و اجرای نهایی موفق شد. چرخش session ID مالکیت را از بین نمی‌برد؛ logout/invalidate آن را حذف می‌کند.

MySQL/هم‌زمانی چندپردازه تازه، مرورگر بصری/موبایل و بانک واقعی در این ثبت محلی اجرا نشده‌اند؛ نتیجه CI مستقل در PR ثبت می‌شود. این ابزار شواهد پذیرش زرین‌پال واقعی نیست. داده، اعتبار و گزارش آزمایشی نباید به دیتابیس تولید منتقل شوند. راه نصب و روشن/خاموش در docs/INSTALL-LOCAL.md.

تاریخ: ۲۰۲۶-۱۰-۲۵. P1/P2/P3 از remote و PRهای باز شماره ۱ تا ۳ بررسی شدند؛ P3 در f9adc63 مبنای شاخه feat/p4-payments-wallet-refunds است. پیش از تغییر، ۷۲ تست / ۴۹۱ assertion پایه موفق شد. هیچ merge یا استقرار روی هاست انجام نشده است.

## آزمون محلی

- مجموعه کامل پیش از آخرین افزودن تست هدایت HTTP، روی **SQLite و MySQL 8.4.3 هرکدام ۱۰۶ تست / ۷۵۲ assertion موفق** داشت. سپس تغییر محدود CSP و هدایت ۳۰۳ و تست آن افزوده شد؛ مجموعه مرتبط نهایی P4 روی **هر دو DB، ۳۰ تست / ۲۴۱ assertion موفق** داشت. اجرای کامل نسخه نهایی در CI جداگانه در PR گزارش می‌شود؛ عدد ۱۰۶ نتیجه اجرای قبلی است و با اجرای کامل ۱۰۷ تست نهایی اشتباه نشود.
- مجموعه مستقل MySQL واقعی: **۲۱ تست / ۱۴۹ assertion موفق**؛ ۱۱ سناریوی جدید مالی به‌اضافه ۱۰ تست رزرو/OTP/شیفت قبلی. از دو پردازش مستقل PHP و barrier مشترک استفاده شد. تست callback تکراری، انتظار واقعی دو thread در performance_schema.data_lock_waits را پیش از آزادسازی قفل والد مشاهده می‌کند.
- رقابت‌های مالی: callback یکسان، callback در برابر لغو، callback در برابر انقضا با اعتبار رزروشده، دو مصرف یک موجودی در روزهای متفاوت، refund در برابر مصرف، دو refund هم‌کلید/ناهم‌کلید، رد در برابر تکمیل استرداد، دو دریافت حضوری، شروع هم‌کلید و دو لغو پرداخت‌شده. receipt/ledger اضافی، موجودی منفی یا تخصیص دوگانه ساخته نشد.
- تست‌های feature شامل مالکیت/IDOR، مجوز مدیر/منشی، CSRF و معافیت محدود callback، جعل authority/status/amount، replay کلید، ۱۰۰/۱۰۱ زرین‌پال، ref_id نامعتبر/برخورد مرجع، verify مبهم و inquiry، timeout، تأخیر/لغو/تعطیلی، snapshot قیمت/مدت، مصرف کامل/ترکیبی اعتبار، برگشت کامل فقط یک بار، rollback کامل لغو در خطای DB و عدم افشای binding، حالت اضطراری و انقضای آن، مانده دقیق حضوری، refund و سند دستی است.
- migration جدید در آزمون step=1 rollback/reapply، نوبت و بیمار P3 را حفظ و بدهی unpaid را از قیمت قبلی پر کرد. اجرای مستقل migrate --seed → rollback همه هفت migration → migrate --seed نیز موفق شد؛ این دیتابیس مصنوعی بود. هیچ داده یا بکاپ مالی واقعی rollback/restore نشد.
- Pint با cache مستقل موفق؛ syntax **۱۲۴ فایل PHP** در app/bootstrap/config/database/routes/tests/lang، syntax سه JS موجود، Composer validate --strict و audit وابستگی production موفق بودند. Blade view:cache و view:clear موفق؛ git diff --check خطای فاصله‌گذاری نداشت. وابستگی جدید Composer/Node اضافه نشد.

## ایرادهای پیدا و اصلاح‌شده

در اولین اجرای تست جدید، نام کمک‌تابع callback با متد final در PHPUnit برخورد داشت و مجموعه اجرا نشد؛ به receiveCallback تغییر کرد. در اولین اجرای کامل MySQL، ۲۵ تست جدید به‌دلیل نوبت مصنوعیِ باقی‌مانده از آزمون migration با SLOT_UNAVAILABLE شکست خوردند؛ lifecycle جداسازی آن تست با DatabaseMigrations اصلاح شد و اجرای کامل MySQL و هم‌زمانی بعدی موفق شد. این شکست‌ها جزو نتایج موفق شمرده نمی‌شوند. در بازبینی هدایت، CSP فقط روی صفحات پرداخت برای دو میزبان ثابت زرین‌پال اصلاح و پاسخ ۳۰۳ با تست بررسی شد؛ رفتار واقعی مسیر بانکی کامل هنوز نیازمند آزمون محیط هدف است.

## سندباکس واقعی و حدود آن

adapter واقعی علیه https://sandbox.zarinpal.com با merchant UUID مصنوعی، مبلغ آزمایشی ۱٬۰۰۰٬۰۰۰ IRR، callback عمومی example.com و بدون نام/موبایل اجرا شد. request پاسخ معتبر code=100 و authority با prefix=S و طول ۳۶ داد؛ inquiry وضعیت IN_BANK داد. هیچ کارت، پرداخت، verify موفق یا refund واقعی اجرا نشد. authority و UUID آزمایشی در گزارش چاپ/commit نشدند.

اولین probe PHP با GATEWAY_UNCERTAIN کامل نشد؛ PHP portable فاقد CA پیکربندی‌شده بود. دسترس‌پذیری endpoint با HEAD (۴۰۵ و Allow: POST) و درخواست ساختگی جداگانه با پاسخ ۲۰۰/۱۰۰ بررسی شد؛ سپس **همان adapter PHP** با CA معتبر موجود در Laragon و اعتبارسنجی TLS روشن، request و inquiry موفق داشت. هیچ bypass گواهی یا verify=false استفاده نشد. این نتیجه موفقیت اتصال request/inquiry است، نه پرداخت کامل سندباکس.

## مرورگر

سرور فقط روی 127.0.0.1:18080، MySQL آزمایشی و harness بیرون Git اجرا شد. adapter پیامک OTP را فقط در فایل موقت ساختگی گذاشت؛ adapter مالی مسیر بانک را با callback محلی fake جایگزین کرد. مهمان با OTP بدون ساخت حساب وارد شد؛ نوبت ۱٬۰۰۰٬۰۰۰ ریالی را تسویه ساختگی کرد؛ بعد از callback عمومی، صفحه خصوصی قطعی/تسویه‌شده/بدهی صفر نشان داد. لغو با dialog تأیید شد و مبلغ کامل به اعتبار برگشت. درخواست استرداد ۶۰۰٬۰۰۰ ریالی پس از تأیید، available را به ۴۰۰٬۰۰۰ رساند و requested نشان داد. مدیر ساختگی با OTP وارد مدیریت مالی شد و درخواست را rejected کرد. این مسیر هیچ انتقال بانکی واقعی نداشت؛ تکمیل دستی با سند مصنوعی فقط در تست خودکار بررسی شد.

در عرض ۳۲۰×۷۴۰، clientWidth/scrollWidth هر دو ۳۰۵ بود و کارت در عرض صفحه قرار داشت؛ تصویر viewport ذخیره شد. capture تمام‌صفحه در ابزار مرورگر کامل نشد و به‌عنوان شاهد استفاده نمی‌شود. نمای مدیر و فرم اضطراری/استرداد نیز مشاهده شد. سرور پس از بررسی متوقف شد. harness، OTP، fixture، تصویر و دیتابیس در commit/بسته نیستند؛ vendor در Git نیست ولی وابستگی‌های production طبق workflow داخل ZIP قرار می‌گیرند.

## انجام‌نشده‌ها و ریسک عملیاتی

پرداخت با کارت در سندباکس/production، verify و callback موفق واقعی زرین‌پال، استرداد بانکی واقعی یا reverse API، SMS واقعی، استقرار staging/هاست، تست قطع پردازش در محیط واقعی، بار/نفوذ/زوم ۲۰۰٪/موبایل فیزیکی/ممیزی کامل دسترس‌پذیری و بازیابی بکاپ انجام نشده‌اند. استرداد این فاز workflow دستی با سند است؛ تطبیق انتقال واقعی و هویت مقصد نیازمند فرایند امن مطب است. موارد بدون authority پس از timeout/crash اولیه نیازمند بررسی پنل پذیرنده‌اند. gateway پیش‌فرض disabled است. APP_KEY و snapshotهای رمزگذاری‌شده باید حفظ شوند و query callback در access log/analytics ثبت نشود. rollback مالی روی داده واقعی مخرب است. این گزارش گواهی انتشار عمومی یا امنیت کامل نیست.
