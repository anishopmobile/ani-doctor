# Homepage contact and clinic location

The default homepage `#contact` now supports the three supplied models: `clinic` (light, contact cards, form/location card), `dark` (teal, white cards, gold appointment CTA), and `pastel` (organic frame, pink accents, message form). Other pages, section visibility/order and published page-builder homepage precedence retain their behavior.

## Real content and images

Title, introduction, address, primary/secondary phone, public email, hours and official website use existing theme settings. Missing optional values produce no fabricated contact cards. Hours are public copy, not booking capacity. WhatsApp appears only when an approved HTTPS WhatsApp link is published in the existing social-link editor. The map button uses the stored validated HTTPS map URL; no fake map, inferred coordinates or third-party iframe/tracking request is loaded. The light location card shows the actual stored address, and opens the configured real map when available.

The independent `contact` media slot in the identity-media editor requires alt text and permits existing raster formats/2MB limit. Upload/replacement leaves that slot unpublished until explicit approval through the publication checkbox; published deletion is blocked. Owner ID 1, authorization, CSRF and settings version protections are reused. Public rendering chooses the published contact image, then published physician portrait, then existing local WebP; missing/unsupported files and HTTP image failures have a safe local fallback. Reference photos/sample addresses and medical-response-time claims are not automatically published. Upload the clinic's approved image through management. A floating image caption is optional and editable.

## Real message workflow

The light/pastel forms submit to `POST /contact/messages`, with CSRF, server validation, Persian/Arabic digit normalization, honeypot and per-IP limits (3/minute, 20/day). A UUID submission hash prevents duplicate storage on retry. Success is shown only after storage; a message does not book an appointment or send email/SMS. Failure uses a separate error bag and returns to `#contact`. Name, phone and body are not flashed back into the session on validation failure. The form can be disabled independently; disabled/hidden contact sections reject submissions.

`website_contact_messages` stores encrypted name/phone/body, a unique submission hash, read status and timestamps. No patient/account/IP/medical-record linkage is created. The model hides private fields from automatic serialization. Only the existing `website.manage` permission grants access to the no-store inbox at `/admin/website-contact-messages` and CSRF-protected read/delete operations. No public message-read endpoint exists. The sidebar and website workflow link to the inbox. Administrators should delete messages no longer needed after handling them; no automatic retention period or medical advice is inferred.

## Installation and verification

Run `php artisan migrate --force` during the normal authorized deployment, before enabling/using the new form. This adds one independent table and changes no existing schema/data. Rolling this migration back deletes inbox messages, so preserve needed records before rollback. Existing JSON theme/media storage holds model selection and images. No new dependency, frontend build or production seed is needed.

The unchanged baseline passed 351 PHPUnit tests / 2,875 assertions. The updated full regression suite passed 357 tests / 3,028 assertions, including the additional validation-output assertions. Dedicated tests cover layouts, real optional content, link validation, preview, publication independence, encrypted/idempotent guest submission, private authorization, escaping, read/delete, rate limits, honeypot, CSRF, absent media, visibility and page-builder priority. Previous rollback-chain tests now explicitly roll back/assert removal of the new inbox table before retaining all original migration/data-preservation checks.

The dedicated Chromium suite uses only the guarded synthetic SQLite fixture: all three models saved through the real enhanced admin control, 18 layout/viewport combinations, 200% text, contact/map/social URLs, image failure, private preview, actual guest submission followed by authorized inbox read/delete, asset isolation and CSP. Desktop/mobile screenshots use explicitly synthetic content and existing local artwork. The release workflow runs this suite after all previous browser checks, plus its PHP/MySQL, migration, packaged HTTPS staging and security checks.
