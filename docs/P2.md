# P2 — خدمات، برنامه کاری و تقویم

## مبنا و دامنه

P1 در شروع بررسی شد: PR شماره ۱ هنوز draft و باز، main در commit f504959 و شاخه P1 در b54aa0e بود. ۲۷ تست P1 دوباره موفق شد. شاخه P2 از P1 ایجاد شده و PR آن باید فعلاً بر شاخه P1 باشد؛ ادغام P1 یا main بخشی از این کار نیست.

مرجع: FR-SRV-01، FR-SCH-01/02/03، FR-CAL-01، AC-SCH، AC-HOL و BR-03/09/15. مالک‌ها Catalog، Scheduling و ثبت ممیزی پیکربندی در SettingsAudit هستند. Patients، OTP و پرداخت تغییر کاربردی ندارند. انتساب فرم خدمت در P6 است؛ رزرو/hold/ویرایش نوبت در P3 است.

## داده و مجوزها

- services با بایگانی نرم، تعرفه صحیح IRR، مدت، فاصله، ظرفیت، فعال و اینترنتی؛ service_price_histories با actor و زمان UTC. تغییر تعرفه تاریخچه جدید ایجاد می‌کند؛ بایگانی تاریخچه را حذف نمی‌کند.
- weekly_schedules با weekday یکتای ISO (دوشنبه=۱، یکشنبه=۷)؛ work_shifts با دقیقه شروع/پایان روز محلی، گام مستقل و ظرفیت. روز تعریف‌نشده یا is_closed تعطیل است. وقفه با چند شیفت غیرهم‌پوشان ساخته می‌شود؛ شیفت تا 24:00 مجاز و عبور از نیمه‌شب رد می‌شود.
- schedule_exceptions با تاریخ میلادی محلی شروع/پایانِ شامل روز آخر، kind=closed|override، شیفت‌ها و دلیل داخلی. محدوده‌های استثنا هم‌پوشانی ندارند. برای اصلاح، حذف آگاهانه و ایجاد دوباره از UI انجام می‌شود. override بر تعطیلی/برنامه هفتگی مقدم است.
- schedule_state یک ردیف پایدار قفل و نسخه تغییر و horizon_days دارد. پیش‌فرض افق ۳۰ روز **با احتساب امروز** است؛ آخرین روز today+29. مدیر ۱ تا ۳۶۵ روز را تنظیم می‌کند؛ منشی اجازه تغییر این سیاست ندارد.
- configuration_audit_events فقط از AuditService و داخل تراکنشِ تغییر نوشته می‌شود؛ actor، before/after و زمان UTC دارد. مسیر ویرایش/حذف این رویدادها وجود ندارد.

catalog.manage فقط مدیر؛ schedules.manage مدیر و منشی؛ schedules.settings فقط مدیر. بیمار، مهمان، حساب غیرفعال و تأییدنشده مجوز مدیریت ندارند. Gate در backend، FormRequest و CSRF اعمال می‌شوند. شماره/نام بیمار و دلیل داخلی استثنا در API عمومی وجود ندارند.

## محاسبه ظرفیت و مرز P3

AvailabilityService برنامه هفتگی و استثناهای بازه را یکجا می‌خواند. SlotCalculator تابع مستقل با بازه‌های نیمه‌باز [start,end) و sweep روی همه مرزهای overlap است؛ شمارش صرفِ تعداد نوبت‌های برخوردکننده استفاده نمی‌شود. ظرفیت هر قطعه حداقل ظرفیت خدمت، شیفت و محدودیت snapshot رزروهای فعال آن قطعه است. مدت+buffer باید در همان شیفت جا شود؛ buffer در طول اشغال لحاظ می‌شود و end_at_utc پایان خود خدمت است.

BookingReadInterface فقط بازه اشغال و وضعیت را می‌خواند: start_at/end_at دارای timezone، status و hold_expires_at و capacity_limit اختیاری. **end_at در این قرارداد شامل buffer رزرو موجود است.** confirmed و pending_payment با انقضای مطلق بزرگ‌تر از زمان سرور ظرفیت را اشغال می‌کنند. سایر وضعیت‌ها و hold دقیقاً منقضی نادیده گرفته می‌شوند. این منطق با fake قراردادی تست شده است.

در P2 جدول و ایجاد رزرو وجود ندارد؛ adapter تولیدی NoBookingsYet صادقانه مجموعه خالی برمی‌گرداند. **P3 باید این binding را به reader واقعی Booking تبدیل کند** و قفل مشترک/مرز اتمیک رزرو و تغییر برنامه را برقرار سازد. این صفحه تضمین ظرفیت هنگام رزرو نیست. تست P2 اثبات عدم double-booking یا تغییر هم‌زمان برنامه با رزرو واقعی نیست.

تغییر برنامه هفتگی، ثبت استثنا و حذف آن، در صورت وجود نوبت قطعیِ متأثر از reader، شمار نوبت‌ها را با خطای فارسی اعلام و confirm_affected را لازم می‌کنند؛ هیچ عملیات نوشتن/حذف روی نوبت انجام نمی‌دهند. تغییر هفتگی تا ۳۶۶ روز آینده را بررسی می‌کند (بیشترین افق مجاز). در P2 بدون جدول رزرو، تعداد واقعی صفر است؛ سناریوی غیرصفر با port fake آزموده شده است. دو ثبت استثنای هم‌پوشان با قفل schedule_state سری می‌شوند و فقط یکی موفق می‌شود.

## رابط‌ها

- GET /calendar: انتخاب خدمت عمومی فعال/اینترنتی، Pardis inline همیشه قابل مشاهده، ماه جاری سرور به وقت تهران، بدون input تاریخ یا popup.
- GET /api/v1/calendar?service_id=…&month=1405-08: روزهای ماه شمسی با date میلادی، jalali و status؛ بدون slot یا داده شخصی.
- GET /api/v1/availability?service_id=…&date=2026-10-28: وضعیت روز و DTO ساعت‌ها (UTC، زمان محلی، ظرفیت و دلیل عدم دسترسی).
- پاسخ‌ها: success/data/error/meta؛ meta دارای server_now، timezone و preview_only=true. خطای ورودی ۴۲۲، خدمت مخفی/ناموجود ۴۰۴، محدودیت درخواست ۴۲۹. سقف API هر IP شصت درخواست در دقیقه است.
- /admin/services: ایجاد/ویرایش/بایگانی خدمت؛ /management/schedule: برنامه هفتگی، تعطیلی تکراری، استثنا و افق رزرو. فرم‌ها SSR، تغییرات POST/PUT/DELETE با CSRF هستند.

JS فقط نمایش/انتخاب و درخواست Fetch می‌کند. با تغییر خدمت، ساعت روز انتخابی دوباره محاسبه می‌شود. درخواست قبلی با AbortController لغو، پاسخ ماه کهنه با revision رد و timeout ده‌ثانیه‌ای به retry تبدیل می‌شود. loading، خطا، empty، روزهای تعطیل/پر/گذشته/خارج افق و انتخاب ساعت نمایش داده می‌شوند؛ انتخاب ساعت هیچ hold یا نوبتی نمی‌سازد. متن API با textContent درج می‌شود.

تقویم از ES module آماده و بدون وابستگی Pardis با commit ثابت 63cab98c0a5d2c37db11faa87392a582c7679966 و مجوز MIT استفاده می‌کند؛ نام نسخه در منبع 3.0.0 بود، اما npm فقط 1.0.2 داشت، بنابراین فایل‌های lib از commit ثابت رسمی دریافت شدند. هیچ npm build یا CDN زمان اجرا اضافه نشده است. CSS اختصاصی موبایل، متن وضعیت روز و برچسب صفحه‌خوان افزوده شده؛ فایل upstream تغییر نکرده است. Intl PHP برای تبدیل جلالی سخت‌گیرانه لازم و در composer ثبت شده است؛ تاریخ نامعتبر roundtrip نمی‌شود.

## ارتقا و rollback

پس از بازبینی و بکاپ روی محیط هدف: composer install، php artisan migrate، php artisan db:seed --class=RoleSeeder. تغییر مجوزها با seeder انجام می‌شود؛ کاربر کارکنان خودکار ایجاد نمی‌شود. هیچ داده نمونه برای production seed نمی‌شود. اجرای migration/هاست خودکار در درخواست وب نداریم.

Rollback آخرین migration جداول خدمات، تاریخچه تعرفه، برنامه/استثنا، وضعیت و audit پیکربندی را حذف می‌کند؛ برای داده واقعی مخرب است و نیازمند بکاپ/بررسی. تست‌ها فقط دیتابیس دورریختنی را migrate/rollback می‌کنند. [شواهد واقعی](P2-VALIDATION.md).
