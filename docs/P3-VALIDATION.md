# گزارش واقعی اجرای P3

تاریخ: ۲۰۲۶-۱۰-۲۵. مبنا: P2 در cc57dc8 و P1 در b54aa0e؛ هر دو PR در آغاز باز و draft بودند، main فقط اسناد داشت. قبل از تغییرات، ۴۸ تست / ۳۱۲ assertion قبلی موفق شد. هیچ استقرار یا merge انجام نشده است.

## نتایج محلی

- PHP 8.4.27 و Laravel وابستگی‌های قفل‌شده؛ SQLite: **۷۲ تست / ۴۹۱ assertion موفق**.
- MySQL 8.4.3 محلی و دیتابیس کاملاً آزمایشی: **۷۲ تست / ۴۹۱ assertion موفق**.
- مجموعه مستقل MySQL در phpunit.mysql.xml: **۱۰ تست / ۶۹ assertion موفق**؛ شامل ۷ سناریوی جدید رزرو و ۳ سناریوی قبلی OTP/شیفت است.
- P3 شامل ۲۳ تست رفتار/امنیت با ۱۷۰ assertion و یک تست migration با ۹ assertion است. علاوه بر مسیر موفق، IDOR خواندن/لغو/تغییر، بیمار غیرمجاز، حساب غیرفعال، CSRF، مجوز تنظیمات و override، سقف رزرو، نسخه قدیمی، کلید تکراری و برخورد کلید بین نوبت‌ها، خطای دیتابیس بدون افشای SQL، انقضا در مرز دقیق و درخواست مجدد، لغو مالی محافظت‌شده و snapshot تغییر زمان بررسی شده‌اند.
- تست migration روی دیتابیس آزمایشی، rollback یک migration مربوط به P3 و اجرای مجدد را همراه با حفظ رکوردهای users/patients/services تأیید می‌کند. اجرای مستقل migrate --seed، migrate:rollback و migrate --seed نیز موفق شد؛ در اجرای نهایی rollback آخرین batch شامل migration P3 بود. این نتیجه ادعای بازیابی بکاپ یا rollback داده واقعی نیست.
- Pint موفق؛ syntax تمام **۹۹ فایل PHP** در app/bootstrap/config/database/routes/tests موفق؛ بررسی syntax سه فایل calendar.js، auth.js و booking.js و Composer validate --strict موفق؛ git diff --check بدون خطای فاصله‌گذاری.

## آزمون هم‌زمانی

پردازش‌های مستقل PHP با barrier مشترک علیه InnoDB واقعی اجرا شدند: آخرین ظرفیت، replay کلید یکسان، دو تغییر به یک ظرفیت، سقف بیمار با اپراتور/روز متفاوت، سقف شماره رزروکننده با بیمار/اپراتور متفاوت، لغو در برابر تغییر با نسخه یکسان، و انقضا در برابر تخصیص مجدد. تست آخرین ظرفیت، پیش از آزادسازی قفل والد، انتظار واقعی دو thread مستقل را در performance_schema.data_lock_waits مشاهده می‌کند؛ سپس فقط یک درخواست موفق می‌شود. خواندن ظرفیت داخل تراکنش از locking current read استفاده می‌کند تا snapshot قدیمی REPEATABLE READ ظرفیت آزاد کاذب نسازد. تست monitor ابتدا با innodb_trx نتیجه قابل اتکا نداد و با data_lock_waits اصلاح و دوباره اجرا شد.

یک فراخوانی بررسی نهایی به اشتباه نام فایل تنظیمات ناموجود phpunit.integration.xml را داشت و اجرا نشد؛ نام صحیح phpunit.mysql.xml است و اجرای صحیح جداگانه انجام شد. این فراخوانی ناموفق جزو نتایج موفق شمرده نمی‌شود.

## مرورگر

مرورگر واقعی علیه سرور محلی و MySQL آزمایشی بررسی شد. adapter پیامک فقط در harness بیرون مخزن با کد ساختگی جایگزین شد؛ پیامک واقعی ارسال نشد. مسیر OTP مهمان، انتخاب بیمار مستقل از حساب، انتخاب روز شمسی و ساعت AJAX، ارسال صریح hold و نمایش unpaid/pending_payment بررسی شد. تغییر ۱۷:۰۰ به ۱۷:۳۰ با هم‌پوشانی خود نوبت موفق شد و مهلت اولیه hold تمدید نشد. برای لغو، dialog درون صفحه، انصراف بدون لغو، سپس تأیید با ثبت وضعیت cancelled مشاهده شد. در عرض ۳۲۰ و ارتفاع ۷۴۰، عرض محتوا و scroll هر دو ۳۰۵ بود و overflow افقی دیده نشد. ایراد فعال‌شدن زودهنگام دکمه رزرو هنگام pageshow اصلاح شد؛ تأیید بومی مرورگر نیز با dialog قابل کنترل و مدیریت فوکوس جایگزین شد. سرور مرورگر پس از بررسی متوقف شد.

تصویر hold فقط داده مصنوعی دارد و بیرون مخزن در پوشه ابزار محلی ذخیره شده است؛ هیچ کد OTP، دیتابیس، harness، داده بیمار واقعی یا vendor به commit اضافه نشده است.

## حدود شواهد

ارسال واقعی SMS.ir، پرداخت زرین‌پال، اعتبار/استرداد، رزرو قطعی مالی یا اضطراری، استقرار هاست/staging، تست بار، بازیابی بکاپ، دستگاه موبایل فیزیکی، زوم ۲۰۰٪ و ممیزی کامل دسترس‌پذیری اجرا نشده‌اند. تمام ایجادهای HTTP این فاز حتی منشی، hold موقت و unpaid هستند؛ لغو مالی تا P4 با خطای بدون اثر متوقف می‌شود. حضور و وضعیت انجام خدمت مربوط به P5 است. انتخابگر بیمار فعلاً حداکثر ۱۰۰ پیوند مجاز را نمایش می‌دهد؛ جست‌وجوی کامل پرونده در محدوده P5 است. کلید APP_KEY برای hash مالکیت باید پایدار بماند؛ چرخش آن نیازمند مهاجرت hashها است.
