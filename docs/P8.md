# P8 — سخت‌سازی، پذیرش عملیاتی و بازیابی

دامنه این شاخه فقط P8 جدول فازهای PRD است: NFR-02/05/06/07 و SEC-01 تا SEC-12؛ روی P7 commit `3de6128f4bf38e2ad04224c45c8e9f406acbe43f`. همه PRهای P1 تا P7 هنگام شروع open/draft و merge‌نشده بودند. این تغییر قابلیت تجاری، پزشک، پرداخت یا فرم تازه اضافه نمی‌کند. [شواهد واقعی و موارد انجام‌نشده](P8-VALIDATION.md).

## سخت‌سازی

- ProductionGuard فقط در production فعال است: HTTPS، Host برابر APP_URL، debug خاموش، نشست Secure/HttpOnly/رمزگذاری‌شده و SameSite مجاز؛ تنظیم نامعتبر پاسخ عمومی 503، Host جعلی 421 و HTTP برابر 426 دارد. HTTP به مقصد برگرفته از Host یا همراه query حساس redirect نمی‌شود.
- ConfiguredProxies جای اعتماد ضمنی framework را می‌گیرد. `OPS_TRUSTED_PROXIES` پیش‌فرض خالی؛ فقط IP/CIDR صریح و معتبر، بدون `*` یا `/0`. تنها Forwarded-For/Proto/Port از این IPها پذیرفته می‌شود؛ Forwarded-Host و Prefix پذیرفته نمی‌شوند. پراکسی باید Host اصلی را حفظ کند و دسترسی مستقیم به upstream محدود باشد. IP فهرست را از مسئول زیرساخت بگیرید؛ مقدار کاربر/هدر منبع تنظیم نیست.
- هدرهای امنیتی و no-store/private برای خطاها هم اعمال می‌شوند؛ دسترسی camera/microphone/geolocation بسته است. `OPS_HSTS_ENABLED` فقط پس از تأیید TLS کامل فعال شود؛ یک سال، بدون includeSubDomains/preload خودکار.
- خطای SQL در همه مسیرها، از جمله ورود، فقط SQLSTATE معتبر می‌نویسد. exception عمومی production فقط نام کلاس را ثبت می‌کند؛ message/trace/arguments/URL ممکن است داده خصوصی داشته باشند. این کاهش جزئیات، عیب‌یابی را محدود می‌کند؛ تشخیص حادثه باید از شناسه‌های audit مجاز و بررسی خصوصی زیرساخت باشد. لاگ خام request/body/provider اضافه نشده است. لاگ پیش‌فرض روزانه با retention فنی ۱۴ روز؛ این عدد ادعای الزام قانونی نیست.
- نمونه Apache/PHP در deployment برای محیط پذیرش است: DocumentRoot=public، عدم index، محدودیت بدنه، بدون نمایش خطا/نسخه PHP و حذف query از access log. Dockerfile.staging گواهی کوتاه‌عمر localhost می‌سازد؛ این گواهی/تصویر برای هاست عمومی مناسب نیست.

## ابزارهای کنسول

`php artisan ops:check` تنها شناسه کنترل و pass/fail می‌دهد: production/debug، origin، APP_KEY، نشست، DB/cache مشترک، MySQL/InnoDB/UTC، migration، مسیر خصوصی، نوشتن runtime، heartbeat و کلید مستقل بکاپ. خروجی نام دیتابیس/مقصد/کلید/پاسخ پزشکی ندارد. ready تنها به معنی کنترل پیکربندی محلی است؛ صحت TLS خارجی، provider، backup/restore و تأیید حقوقی جدا لازم‌اند.

`ops:heartbeat` هر دقیقه از Scheduler ثبت می‌شود؛ بیش از ۱۸۰ ثانیه تأخیر، readiness را fail می‌کند. اجرای دستی آن فقط ابزار تست/راه‌اندازی است و اثبات cron واقعی هاست نیست. DB cache و session مشترک‌اند؛ array/file برای production پیشنهاد این فاز نیستند. `ops:*` هیچ route وب ندارد.

## بکاپ رمزگذاری‌شده

ماژول Operations در Application/Infrastructure، بدون migration جدید. `OPS_MYSQLDUMP_BINARY` و `OPS_MYSQL_BINARY` ابزار رسمی MySQL 8 هستند؛ MariaDB client یا SQLite با این قرارداد پشتیبانی نمی‌شوند. تنظیم DB باید صریح باشد؛ DB_URL برای جلوگیری از اختلاف client/PDO رد می‌شود. TLS CA از پیکربندی cache‌شده PDO هم حفظ و در client با VERIFY_IDENTITY استفاده می‌شود.

1. کلید مستقل بسازید: `php artisan ops:backup-key /private/key-escrow/backup.key`. فایل موجود جایگزین نمی‌شود؛ کلید چاپ نمی‌شود. در Unix فایل 0600 است؛ ACL ویندوز را اپراتور باید جدا بررسی کند.
2. `OPS_BACKUP_KEY_FILE` و `OPS_BACKUP_DIR` را خارج public تنظیم کنید؛ کلید بیرون پوشه بکاپ و `storage/app/private` باشد. کلید بکاپ با APP_KEY یکی نباشد. نسخه امن APP_KEY را جدا escrow کنید و آن را در استقرار بعدی تغییر ندهید.
3. در بازه نگهداری: درخواست‌های نوشتنی را متوقف/تخلیه، cron/worker فعال و هر نویسنده بیرونی را متوقف کنید؛ `php artisan down --retry=60`، سپس `php artisan ops:backup --writers-stopped`. این flag تأیید مسئول عملیات است، نه کشف خودکار نویسنده خاموش. در پایان عملیات، وضعیت خروج را بررسی و `php artisan up` و scheduler/worker را برقرار کنید؛ `finally` بیرونی برای خارج‌شدن از maintenance لازم است.
4. همه جدول‌ها باید InnoDB باشند. mysqldump با single-transaction/quick/hex-blob، بدون تماس provider اجرا می‌شود. credential فقط در فایل موقت 0600 داخل پوشه 0700 و نه argv است؛ خطای خام client/SQL چاپ نمی‌شود.
5. SQL مستقیماً به رکوردهای AES-256-GCM می‌رود؛ dump plaintext در مسیر بکاپ ساخته نمی‌شود. فایل‌های `storage/app/private` در همان بازه توقف نوشته‌ها اضافه می‌شوند. backup با پسوند `.adb`، نام تصادفی، checksum و انتشار اتمیک پس از موفقیت کامل است. فایل part در شکست پاک می‌شود. بدون پنجره توقف، هماهنگی DB/فایل تضمین نمی‌شود.

فرمت نسخه‌دار، salt مستقل برای HKDF، nonce شمارنده یکتا، AAD، tag هر رکورد و final اجباری دارد؛ حذف انتها، جابه‌جایی، الحاق، خرابی و کلید غلط رد می‌شوند. مسیر traversal و symlink مجاز نیست. APP_KEY در فایل نیست؛ fingerprint آن داخل محتوای رمزگذاری‌شده است. از دست رفتن هرکدام از کلیدها ممکن است بازیابی را ناممکن کند. فرمت جای بازبینی مستقل رمزنگاری یا مدیریت حرفه‌ای کلید را نمی‌گیرد.

سیاست پیشنهادی عملیاتی: روزانه و پیش از ارتقا، یک کپی رمزگذاری‌شده خارج هاست، ۷ روز روزانه و ۴ هفته هفتگی؛ فقط پس از تأیید مسئول/الزام محل اعمال شود. P8 حذف خودکار بکاپ یا داده بیمار و cron ایجاد downtime روی هاست نصب نمی‌کند. مالک، زمان‌بندی روزانه، فضای آزاد، off-site، اعلان شکست و آزمون فصلی باید در محیط واقعی تعیین شوند. زمان پاک‌سازی قانونی داده درمانی/مالی در این PR تعیین نشده است.

## بازیابی جدا و بازگشت نسخه

اپراتور دیتابیس **خالی** `ani_doctor_restore_<suffix>` و حساب **مجزا از حساب فعال برنامه** را ایجاد کند. `OPS_RESTORE_DB_USERNAME` و `OPS_RESTORE_DB_PASSWORD` فقط در محیط امن تنظیم شوند. حساب بازیابی فقط روی همان DB مقصد مجوز داشته باشد؛ global privilege، role، grant option یا مجوز DB دیگر رد می‌شود. underscore نام دیتابیس در GRANT باید طبق MySQL به‌صورت literal escape شود، نه wildcard. برنامه SHOW GRANTS همان حساب را پیش از import بررسی می‌کند؛ حتی SQL دارای USE دیتابیس فعال با مجوز سرور محدود می‌ماند. این محدودیت عمداً حساب root/حساب مشترک را برای restore نمی‌پذیرد. سپس با APP_KEY اصلی و کلید بکاپ:

```text
php artisan ops:restore /private/backups/backup.adb ani_doctor_restore_drill /private/drill/restored-files --isolated-target
```

مقصد برابر DB فعال، نام خارج prefix، مقصد دارای جدول و پوشه فایل موجود/داخل storage فعال رد می‌شوند. همه tagها، checksumها، manifest و APP_KEY قبل از اولین نوشتن در دیتابیس مقصد بررسی می‌شوند. برای restore، SQL plaintext موقت فقط در پوشه خصوصی 0700 و فایل 0600 ساخته و در finally حذف می‌شود؛ این حذف ادعای secure erase رسانه نیست و دیسک رمزگذاری‌شده توصیه می‌شود. فایل‌های خصوصی ابتدا جدا آماده می‌شوند و هیچ پوشه فعالی overwrite نمی‌شود. MySQL restore ذاتاً DDL اتمیک ندارد؛ خطای import ممکن است مقصد جدا را نیمه‌کاره بگذارد. ابزار آن مقصد را فعال یا خودکار حذف نمی‌کند.

پس از بازیابی، نسخه کد/lockfile/schema، رمزگشایی فرم، مالکیت/HMAC، رسید/ledger و گزارش تطبیق، فایل‌ها و مجوزها را بررسی کنید. SMS، gateway و worker در drill خاموش بمانند تا پیام/پرداخت تاریخی اجرا نشود. تعویض اتصال برنامه و promotion فقط پس از بازبینی و مجوز جدا و طرح برگشت انجام شود؛ این ابزار promotion ندارد. RPO/RTO تولیدی باید با حجم/زیرساخت واقعی اندازه‌گیری شوند؛ زمان تست کوچک معادل تضمین تولیدی نیست.

قبل از promotion، **در مقصد جدا** نشست‌های sessions و cache/cache_locks قدیمی را پاک و code_hashهای otp_challenges را null و status را expired کنید؛ بازیابی نباید نشست یا OTP ابطال‌شده پس از زمان بکاپ را دوباره معتبر کند. این مرحله بخشی از تصمیم cutover مسئول عملیات است و ابزار restore که فقط drill می‌سازد خودکار داده احراز هویت یا سوابق را تغییر نمی‌دهد. سپس ورود تازه و heartbeat جدید بررسی شوند. این پاک‌سازی نباید روی DB فعال یا داده مالی/فرم اجرا شود.

## ZIP، نصب و آزمون بار

CI اکشن‌ها را به SHA بررسی‌شده pin می‌کند، dependencies را audit و production-only نصب می‌کند. PackageVerifier وجود فایل‌های لازم، نبود env/کلید/DB/بکاپ/runtime/test/dev dependency و PHP اضافی public را بررسی و RELEASE.json با SHA256 فایل‌ها می‌سازد. `php scripts/verify-package.php --root=/private/extracted` **پیش از افزودن env و runtime/cache** اجرا شود. manifest امضای دیجیتال نیست؛ digest artifact را از اجرای GitHub معتبر مستقل بررسی کنید. این verifier برای ZIP استخراج‌شده است، نه درخت نصب‌شده دارای config cache و env تولیدی.

پس از ساخت ZIP، CI همان ZIP را جدا استخراج، با Apache/PHP رسمی و HTTPS در محیط موقت نصب، migration/seed/optimize و Scheduler را اجرا و smoke/readiness/load را بررسی می‌کند؛ artifact فقط پس از این مرحله منتشر می‌شود. fixture خارج بسته است و فقط روی DB نام‌گذاری‌شده ساختگی با کلید محیط صریح مجاز است. هیچ provider واقعی یا secret تولیدی وارد CI نمی‌شود. base image باید دوره‌ای بازبینی و digest مشاهده‌شده در اجرای ساخت پیگیری شود؛ تصویر staging جای artifact استقرار هاست نیست.

`scripts/load-test.php` فقط HTTPS loopback با CA صریح را قبول می‌کند؛ ۴ هم‌زمان، ۴۰ درخواست روز و ۸ ماه، زیر rate limit فعال ۶۰ درخواست در دقیقه. پاسخ خطا/429/timeout شکست محسوب می‌شود؛ هدف p95 روز حداکثر ۱۰۰۰ms است. تست ظرفیت کل سامانه، بار طولانی، شبکه اینترنت، کاربران واقعی و کارایی provider نیست. قبل از تکرار، پنجره rate limit باید تمام شده باشد. `scripts/staging-smoke.php` TLS، login/health، حفاظت مدیریت، Host، CSRF و فایل‌های ممنوع را با داده مصنوعی می‌سنجد.

## گیت‌های انتشار و تهدیدها

| خطر | کنترل/شاهد | حد باقی‌مانده |
|---|---|---|
| جعل Host/HTTPS/IP و cookie ضعیف | P8HardeningTest و smoke | تنظیم proxy و CA هاست واقعی |
| OTP/IDOR/مجوز منشی | تست‌های P1 تا P7 و CSRF production | ارزیابی مستقل نفوذ و نشست‌های واقعی |
| ظرفیت/پرداخت تکراری | ۴۰ سناریوی رقابت پیشین | بار و قطع اتصال واقعی provider |
| افشای SQL/پاسخ/secret در خطا | redaction و no-store خطا | تنظیم access/error log و retention زیرساخت |
| ZIP آلوده یا تغییر فایل | PackageVerifier و manifest | manifest امضا نیست؛ منشأ artifact بررسی شود |
| بکاپ لو‌رفته/خراب/ناقص | رمزگذاری، tag/final، آزمون بازیابی | escrow/off-site/دیسک/رویه حقوقی واقعی |
| restore روی داده فعال | مقصد خالی جدا، بدون promotion | تصمیم cutover و کنترل نتیجه توسط مسئول |
| cron متوقف یا صف تکراری | heartbeat و idempotency قدیمی | پایش و اعلان خارجی باید تنظیم شود |

SEC-01 تا 08 و 11/12 از مجموعه‌های قبلی همراه regression P8 دوباره اجرا می‌شوند؛ SEC-09 از بسته و SEC-10 از نصب موقت سنجیده می‌شوند. انتشار عمومی همچنان نیازمند محیط/دامنه واقعی، TLS و دسترسی محدود، sandbox واقعی بانک/SMS، تست نفوذ مستقل، privacy policy تأییدشده فارسی، بررسی حقوقی/پزشکی محل و تعهد محرمانگی کارکنان است. این موارد ادعای انجام‌شده این شاخه نیستند.

rollback P8 migration ندارد. کد/پیکربندی قبلی به‌صورت هماهنگ برگردد؛ بکاپ‌ها و کلیدها حذف نشوند. rollback سخت‌سازی می‌تواند حفاظت production را کاهش دهد؛ صرفاً برای بازگشت کنترل‌شده و پس از بررسی مسئول استقرار است.
